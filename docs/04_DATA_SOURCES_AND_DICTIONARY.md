# Data Sources and Data Dictionary
## 1. Purpose
Document the exact MODIS and VIIRS products used, their fields, units, quality flags, versions, and access conditions.

## 2. Candidate Authoritative Sources
- NASA FIRMS: https://firms.modaps.eosdis.nasa.gov/
- NASA MODIS active-fire product information: https://modis.gsfc.nasa.gov/data/dataprod/mod14.php
- NASA VIIRS active-fire product information: https://viirsland.gsfc.nasa.gov/Products/NASA/FireESDR.html

These are starting points. Before implementation, confirm the exact product, version, availability, terms of use, and current download/API procedure.

## 4. Common Internal Data Dictionary
The following is a proposed internal schema. Map each field from the selected source product and retain raw fields separately.

| Internal field | Meaning | Notes |
|---|---|---|
| observation_id | Internal unique row identifier | Generated by application |
| source_record_id | Original source identifier or stable row reference | Preserve when provided |
| source_sensor | MODIS or VIIRS | Controlled vocabulary |
| platform | Satellite/platform name | Product-specific |
| product_name | Exact product identifier | Required metadata |
| product_version | Product/collection version | Required where available |
| observation_time_utc | Observation timestamp normalized to UTC | Keep raw timestamp too |
| latitude | Latitude in decimal degrees | Validate -90 to 90 |
| longitude | Longitude in decimal degrees | Validate -180 to 180 |
| confidence_raw | Original confidence field | Semantics vary by product |
| frp_raw | Original FRP value | Preserve original unit |
| frp_unit | Unit for FRP | Confirm product documentation |
| scan_raw | Original scan/footprint-related field | If available |
| track_raw | Original track/footprint-related field | If available |
| quality_flags_raw | Original quality fields | Preserve source values |
| ingestion_run_id | Processing run that imported the record | Traceability |
| row_quality_status | Valid, warning, rejected | Use documented rules |

## 6. Data Quality Rules
- Check coordinate ranges and null coordinates.
- Parse timestamps according to the product specification, then normalize to UTC.
- Treat sentinel values and missing values according to the relevant product documentation.
- Do not combine confidence values from different sensors as if they have identical meanings.
- Do not convert FRP units or compare FRP values until product semantics and units are confirmed.
- Track all rejected rows and reasons.
- Keep raw input values available for auditing.

## 7. Data Management
- Store dataset version and retrieval date.
- Record checksums where feasible.
- Do not commit large data files or API keys to Git.
- Follow source terms and usage restrictions.
- Use small, clearly labelled test fixtures for automated tests; never present test fixtures as actual observations.
